## 1. Контекст и бизнес-цель

На фулфилменты (ФФ) резко пришёл поток селлеров с запросом на отгрузки по схеме **FBS** (ситуация со складами маркетплейсов). У ФФ нет инструмента, который собирал бы сборочные задания **из всех кабинетов селлеров в одну панель**. Сегодня кладовщик вручную заходит в каждый ЛК, ищет заказы, печатает этикетки — процесс не масштабируется.

**Продуктовая цель:** дать ФФ бесплатный инструмент → быстро занять рынок ФФ → через ФФ получить доступ к их клиентам-селлерам (два API-ключа: на FBS и на данные) → сформировать базу для основного платного продукта.

**Ключевое ограничение проекта:** скорость. Идём по пути «быстро выкатить → получить обратную связь → доработать», без длительного проектирования. Референса на рынке нет — ориентируемся на процессы пилотного ФФ.

### 1.1 Что делает система (в одном абзаце)
Система по API-ключам подключённых кабинетов селлеров периодически забирает новые сборочные задания FBS с Wildberries и Ozon, сводит их в единую ленту с фильтрами (маркетплейс / ИП / магазин / склад отгрузки / статус), позволяет сформировать и распечатать **сборочный лист** для кладовщика, отметить факт сборки, распечатать **этикетки (стикеры)** маркетплейса и передать изменённый статус обратно в кабинет селлера.

## 2. Границы MVP

### 2.1 В объёме (In scope)
- Схема поставки: **только FBS**.
- Маркетплейсы: **Wildberries и Ozon**.
- Подключение кабинетов по API-ключу (заводит администратор системы).
- Чтение сборочных заданий + запись статусов обратно в маркетплейс.
- Получение и печать этикеток/стикеров через API маркетплейса.
- Формирование, печать и учёт сборочных листов.
- Ручное и автоматическое (по таймеру) обновление ленты.
- Выгрузка ленты в XLSX/PDF.

### 2.2 Вне объёма MVP (Out of scope)
| Функция | Почему отложено |
|---|---|
| DBS, DBW, Самовывоз (Click&Collect) | Другие наборы методов и статусов. Пилотный ФФ сейчас перестраивается с FBO на FBS. Добавляем после MVP |
| Ролевая модель (администратор / оператор / сборщик) | На MVP — одна учётка на ФФ, логин передаётся сотруднику. Роли — задача «третьей степени» по приоритету |
| Самостоятельная регистрация ФФ | На MVP аккаунты и API-ключи заводит администратор системы |
| Интеграция с WMS («Мой склад» и т.п.), адресное хранение | Ячейка вводится вручную в поле «Комментарий»/«Ячейка» |
| Работа с грузоместами/коробами, стикеры на короб и паллету | Требует подтверждения процесса у ФФ (см. открытые вопросы) |
| Маркировка «Честный знак», ГТД, IMEI, УИН | Отдельный крупный блок (meta-методы). Не в MVP, но учесть в модели данных |
| Мобильный интерфейс / ТСД | Кладовщик работает с бумажным сборочным листом |

## 3. Роли и пользователи

| Роль | В MVP | Задачи |
|---|---|---|
| **Администратор системы** (наша сторона) | Да, отдельная админка/скрипт | Заводит аккаунт ФФ, вносит API-ключи кабинетов, проставляет теги «ИП» и «Магазин» к каждому ключу |
| **Оператор ленты** (старший кладовщик / администратор склада ФФ) | Да | Фильтрует ленту, формирует сборочные листы, назначает сборщика, печатает стикеры, подтверждает отгрузку |
| **Сборщик / комплектовщик** | Нет отдельной учётки | Работает по распечатанному сборочному листу, отмечает галочками собранное, возвращает лист оператору |
| **Селлер** | Нет | Только предоставляет API-ключ |

> **Важное допущение MVP:** на разных ФФ штат от 1,5 человек до 10, поэтому оператор и сборщик **могут быть одним человеком**. Даже в этом случае сборочный лист печатается — по складу никто не ходит с ноутбуком. Печать сборочного листа обязательна в любой конфигурации.

## 4. Процесс «как будет» (To-Be)

```
[1] Админ подключает кабинет (API-ключ + теги ИП/Магазин)
        ↓
[2] Система по расписанию (30/60 мин) и по кнопке "Обновить"
    тянет новые сборочные задания из WB и Ozon по всем ключам ФФ
        ↓
[3] Оператор фильтрует ленту: маркетплейс → ИП → склад отгрузки → статус "Новые"
        ↓
[4] Оператор выделяет строки → "Сформировать сборочный лист"
    → внутренний статус строк = "В подборе"
    → печать листа (A4), назначен сборщик (ФИО), проставлены ячейки/комментарии
        ↓
[5] Сборщик физически собирает товар, отмечает галочки на бумаге
        ↓
[6] Оператор в панели по листу отмечает: "Собрано" / "Не найдено"
    → внутренний статус = "Собрано" / "Недостача"
        ↓
[7] Оператор передаёт статус в маркетплейс (WB: добавить в поставку /
    Ozon: упаковать отправление) → появляется доступ к стикерам
        ↓
[8] Печать стикеров пачкой → внутренний статус "Стикер напечатан"
    → стикеры клеятся на товар/упаковку
        ↓
[9] Отгрузка: WB — передать поставку в доставку + QR поставки;
    Ozon — сформировать акт/отгрузку → статус "Отгружено"
```

### 4.1 Критическая находка по процессу (ответ на вопрос «в какой момент печатаем стикер»)
На обоих маркетплейсах **стикер физически недоступен, пока отправление не переведено в статус «упаковано / добавлено в поставку»**:

- **Ozon:** этикетка (`package-label`) выдаётся только после вызова метода упаковки заказа (`/v4/posting/fbs/ship`), когда отправление перешло `awaiting_packaging → awaiting_deliver`.
- **Wildberries:** стикеры (`/api/v3/orders/stickers`) выдаются для заданий, уже добавленных в поставку (supplierStatus `new → confirm`). ⚠ *подтвердить на тесте.*

**Следствие для UX:** нельзя «сначала напечатать все этикетки, потом собирать» — порядок обязательно: **собрали → подтвердили в системе → передали статус в МП → получили и напечатали стикеры**. Это нужно проговорить с ФФ на созвоне, т.к. их ожидание может быть обратным.

## 5. Модель статусов

### 5.1 Внутренние статусы системы (единые для обоих МП)

| Код | Название в UI | Транслируется в МП | Описание |
|---|---|---|---|
| `NEW` | Новое | — | Получено из МП, не обработано |
| `IN_PICKING` | В подборе | **Нет** | Включено в сборочный лист, лист отдан сборщику |
| `PICKED` | Собрано | Нет | Сборщик подтвердил наличие товара |
| `NOT_FOUND` | Не найдено | Нет (или отмена) | Товара нет на складе |
| `CONFIRMED` | Передано в МП | **Да** | WB: добавлено в поставку / Ozon: упаковано |
| `LABELED` | Стикер напечатан | Нет | Этикетка получена и отправлена на печать |
| `SHIPPED` | Отгружено | **Да** | WB: поставка передана в доставку / Ozon: отгрузка сформирована |
| `CANCELLED` | Отменено | Да | Отмена продавцом или покупателем |

> **Принципиально:** внутренний статус ≠ статус маркетплейса. Статус «В сборке» на МП мы ставим **только когда товар реально упаковывается**, а не когда лист ушёл сборщику. Отсюда разделение `IN_PICKING` (наш) и `CONFIRMED` (МП).

**Требование:** возможность **отката** внутреннего статуса назад (ошиблись, напечатали, надо переделать) — с журналированием кто и когда откатил. Откат статуса, уже ушедшего в МП, помечается как «требует ручного действия в ЛК» ⚠ *проверить обратимость на стороне API.*

### 5.2 Статусы Wildberries (по факту данных из выгрузки)

`supplierStatus` (ставит продавец):

| Значение | Смысл | Встречается в выгрузке (15 427 строк) |
|---|---|---|
| `new` | Новое сборочное задание | 400 |
| `confirm` | На сборке (добавлено в поставку) | — |
| `complete` | Передано в доставку | 14 242 |
| `cancel` | Отменено продавцом | 785 |

`wbStatus` (ставит WB): `waiting`, `sorted` (1), `sold` (11 964), `canceled` (785), `canceled_by_client` (1 992), `declined_by_client` (399), `defect` (286), `ready_for_pickup`.

### 5.3 Статусы Ozon (`status` / `substatus`)

`awaiting_verification` → `awaiting_approve` → **`awaiting_packaging`** (рабочий вход для ФФ) → **`awaiting_deliver`** (упаковано, готово к отгрузке) → `delivering` → `driver_pickup` → `delivered`; ветки: `cancelled`, `arbitration`, `not_accepted`.

В выгрузке `Заказы_FBS_ArchiDog.xlsx` (137 строк) все записи в `status = delivering`, `substatus = posting_on_way_to_city`, `previous_substatus = posting_transferring_to_delivery` — то есть выгрузка сделана уже после отгрузки; **для теста ленты нужны данные в статусе `awaiting_packaging`.**

### 5.4 Маппинг статусов

| Внутренний | Wildberries | Ozon |
|---|---|---|
| `NEW` | `supplierStatus = new` | `status = awaiting_packaging` |
| `IN_PICKING` / `PICKED` | (только внутри системы) | (только внутри системы) |
| `CONFIRMED` | `confirm` — через добавление в поставку | `awaiting_deliver` — через `/v4/posting/fbs/ship` |
| `SHIPPED` | `complete` — поставка передана в доставку | акт/отгрузка сформирована |
| `CANCELLED` | `cancel` | `cancelled` |

| F-6.5 | Полученные файлы стикеров кэшируются: повторная печать без нового обращения к API | Must |
| F-6.6 | После успешной печати строка переходит в `LABELED`; предусмотрен откат («перепечатать») | Must |
| F-6.7 | Настройка оборудования на уровне ФФ: тип принтера (термо/лазерный), формат вывода, размер этикетки | Should |
| F-6.8 | Стикеры на короб/грузоместо (WB `trbx`), стикер на паллету | Out of MVP ⚠ — подтвердить у ФФ |

### 6.2 U — Usability (удобство)
| ID | Требование |
|---|---|
| U-1 | Основной сценарий (фильтр → выделить → сборочный лист → печать) выполняется **не более чем в 4 клика**. Оператор работает стоя, у монитора на складе |
| U-2 | Все действия доступны с одного экрана — переходов между разделами в основном сценарии нет |
| U-3 | Таблица с фиксированной шапкой, поддержка 1000+ строк без «проваливания» интерфейса; постраничная или виртуальная прокрутка |
| U-4 | Крупные шрифты и контрастные статусы: цветовое кодирование внутреннего статуса (новое / в подборе / собрано / стикер напечатан / проблема) |
| U-5 | Явный индикатор «Обновлено N минут назад» и прогресс синхронизации по кабинетам |
| U-6 | Все действия, ведущие к изменению статуса на маркетплейсе, требуют подтверждения с указанием количества затрагиваемых заданий |
| U-7 | Интерфейс на русском языке; терминология маркетплейсов сохраняется («сборочное задание», «отправление», «поставка») |

### 6.3 R — Reliability (надёжность)
| ID | Требование |
|---|---|
| R-1 | Отказ или таймаут API одного маркетплейса/кабинета не блокирует работу с остальными; в ленте показывается предупреждение по конкретному кабинету |
| R-2 | Очередь исходящих операций с автоматическими повторами (экспоненциальная задержка) и «мёртвой очередью» для ручного разбора |
| R-3 | Полный журнал: кто, когда, какое действие, какой запрос ушёл в МП, какой ответ получен. Хранение — не менее 90 дней |
| R-4 | При потере связи система не теряет уже сформированные сборочные листы и уже полученные файлы стикеров |
| R-5 | Защита от двойной передачи статуса при повторном нажатии кнопки (блокировка на время выполнения + идемпотентность) |
| R-6 | Сверка: фоновая задача сравнивает наши внутренние статусы со статусами МП и подсвечивает расхождения |

### 6.4 P — Performance (производительность)
| ID | Требование |
|---|---|
| P-1 | Отрисовка ленты объёмом до 5 000 строк — не более 2 сек с момента применения фильтра |
| P-2 | Полный цикл синхронизации по одному кабинету — не более 60 сек |
| P-3 | Получение и склейка пачки из 100 стикеров — не более 30 сек |
| P-4 | Соблюдение лимитов API: WB использует **общую квоту на группу методов** «сборочные задания FBS / поставки / пропуска» (ответ 409 засчитывается как 10 запросов), поэтому опрос кабинета не чаще 1 раза в 15 минут, а обогащение карточками — из кэша ⚠ |
| P-5 | Формирование печатной формы сборочного листа на 50 позиций — не более 5 сек |
| P-6 | Целевой профиль нагрузки MVP: 10 ФФ × до 50 кабинетов × до 500 заданий/день ⚠ *уточнить реальные объёмы у пилотного ФФ* |

### 6.5 S — Supportability (поддерживаемость)
| ID | Требование |
|---|---|
| S-1 | Единый внутренний формат «строки ленты», к которому приводятся ответы обоих маркетплейсов; добавление третьего МП не требует переписывания UI |
| S-2 | Адаптеры маркетплейсов изолированы: своя реализация методов чтения, записи статуса и получения этикетки |
| S-3 | Ручной ре-синк отдельного кабинета из интерфейса администратора |
| S-4 | Экспорт любой выборки в XLSX для разбора инцидентов |
| S-5 | Версионирование маппинга статусов — маркетплейсы меняют API несколько раз в месяц |
| S-6 | Мониторинг: доля ошибок API по кабинетам, задержка синхронизации, длина очереди повторов |

### 6.6 «+» — дополнительные ограничения

**Design (проектные)**
- Веб-приложение, desktop-first (кладовщик за стационарным ПК). Адаптив под планшет — Could.
- Мультиарендность: изоляция данных по фулфилментам на уровне БД с первого дня.
- Модель данных сразу закладывает поля под DBS/DBW/Самовывоз, маркировку и грузоместа, даже если функционал отключён.

**Implementation (реализация)**
- Переиспользовать существующие механизмы подключения кабинетов и хранения ключей из основного продукта.
- Печать — через штатный диалог печати браузера (PDF-поток). Прямая печать на принтер по ZPL — вторым этапом, после уточнения парка оборудования ФФ.

**Interface (интеграционные)**
- Wildberries Marketplace API v3 (`https://marketplace-api.wildberries.ru`), авторизация — заголовок `Authorization` с токеном категории «Маркетплейс».
- Ozon Seller API (`https://api-seller.ozon.ru`), авторизация — заголовки `Client-Id` и `Api-Key`.
- Наличие песочниц: WB — `marketplace-api-sandbox.wildberries.ru`; для тестов также предоставляется реальный ключ пилотного ФФ.

**Physical / Legal (эксплуатационные и правовые)**
- API-ключи селлеров хранятся **зашифрованно**, не выводятся в UI после сохранения, не попадают в логи.
- Ключи дают право менять статусы заказов селлера — требуется письменное согласие селлера на передачу ключа фулфилменту и разграничение доступа «ФФ видит только свои кабинеты».
- Продукт для ФФ на старте бесплатный; монетизация — через доступ к базе селлеров в основном продукте.

### 7.3 Ключевые отличия, влияющие на реализацию

| Аспект | Wildberries | Ozon |
|---|---|---|
| Единица работы | Сборочное задание = **1 SKU** (в выгрузке `Количество SKU` = 1 у всех 15 427 строк) | Отправление = **несколько товаров**, требует раскрытия в строки |
| Перевод «на сборку» | Через добавление в **поставку** (отдельная сущность) | Через метод упаковки `ship`, поставки как сущности нет |
| Габариты в заказе | Нет — только `cargoType` | Есть `products.dimensions` в детальном методе |
| Юрлицо селлера | Нет в заказе → **тег кабинета** | Нет в заказе (`legal_info` — покупатель) → **тег кабинета** |
| Дедлайн отгрузки | Нет явного поля → расчёт | `shipment_date` — есть |
| Цены | В копейках | В рублях, строкой |
| Формат этикетки | PNG / SVG / ZPL, 58×40 или 40×30 | PDF |

## 10. Открытые вопросы к пилотному фулфилменту (созвон, среда)

### Процесс
1. Оператор ленты и сборщик — один человек или разные? Сколько человек в смене?
2. Как выглядит цикл сейчас: от появления заказа до передачи в пункт приёма?

## 11. План работ

| Шаг | Результат | Срок |
|---|---|---|
| 1 | Данный документ + функциональный макет ленты | к среде |
| 2 | Созвон с пилотным ФФ: валидация процесса, закрытие вопросов из п. 10 | среда |

| 6 | Итерации в течение августа: роли, DBS/DBW, короба, маркировка | август |

**Риски**
| Риск | Влияние | Смягчение |
|---|---|---|
| Порядок «сборка → подтверждение → стикер» не совпадёт с ожиданием ФФ | Переделка ключевого сценария | Проговорить на созвоне п. 4.1 **до** разработки |

| Лимиты API WB (общая квота на группу FBS-методов) при 50+ кабинетах | Отставание ленты от реальности | Кэш карточек, разнесение опроса по расписанию, ручное обновление как приоритетный канал |
| Парк принтеров требует прямой ZPL-печати | Печать из браузера не подойдёт | Вопросы №8–10; WB отдаёт ZPL нативно |
| Частая смена версий методов Ozon | Поломка интеграции | Изоляция адаптеров, мониторинг раздела «Новости» API |
